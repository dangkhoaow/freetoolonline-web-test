Text vs Line vs Word vs Git Diff

Zuletzt geprüft 2026-04-27. Öffnen Sie das text-diff-Tool, um zwei Strings, Dateien oder eingefügte Blöcke in Ihrem Browser zu vergleichen.

30-Sekunden-Antwort. Vier Arten von Diff beantworten jeweils eine andere Frage. Text-Diff: sind diese beiden Strings byte-gleich, und wenn nicht, wo unterscheiden sie sich? Line-Diff: welche Zeilen haben sich geändert (der Standard für Code-Review). Word-Diff: welche Wörter haben sich innerhalb geänderter Zeilen geändert (der Standard für Prosa). Git-Diff: welche Zeilen haben sich zwischen zwei Commits in der verfolgten Historie geändert (Line-Diff plus Versionskontroll-Kontext).

Die vier Geschmacksrichtungen und wofür jede ist

  • Text-Diff (String-Diff). Der einfachste. Vergleichen Sie zwei Strings oder zwei Textblöcke Zeichen für Zeichen. Ausgaben: die Stellen, wo sie sich unterscheiden. Richtig für "sind diese beiden eingefügten Blobs wirklich identisch?" - JSON-Konfigurations-Drift, Fehlermeldungen in Support-Tickets, Log-Zeilen, die übereinstimmen sollten.
  • Line-Diff. Der Standard für Code. Behandeln Sie jede Zeile als die Änderungseinheit. Ausgabe: welche Zeilen hinzugefügt, entfernt oder modifiziert wurden. Die "+" / "-"-Ausgabe, die jedes Code-Review-Tool verwendet. Starker Standard, wenn der zugrunde liegende Inhalt zeilenstrukturiert ist.
  • Word-Diff. Richtig für Prosa. Wenn ein Satz ein einzelnes Wort ändert, zeigt Line-Diff den gesamten Satz zweimal (einmal - und einmal +). Word-Diff hebt nur das geänderte Wort hervor. Besser für redaktionelle Prüfung und Inhaltsänderungen.
  • Git-Diff. Line-Diff plus Repository-Historie. Vergleicht zwei Commits, zwei Branches, working-tree-vs-index oder index-vs-HEAD. Fügt Datei-Modus-Erkennung, Umbennen-Erkennung und Binärdatei-Handhabung hinzu, die reines Line-Diff fehlt. Wird innerhalb von Versionskontroll-Workflows verwendet.

Wann Line-Diff falsch ist

Line-Diff scheitert, wenn die Zeilen selbst lang sind. Bearbeiten Sie ein Wort in einer 200-Zeichen-Zeile und das Diff zeigt die gesamte Zeile als entfernt-und-neu-hinzugefügt - kein Signal darüber, welches Wort tatsächlich geändert wurde. Dasselbe für einzeiliges JSON oder minifizierten Code, wo alles auf einer einzigen Zeile ist.

Zwei Korrekturen: formatieren Sie die Eingabe zuerst neu (pretty-print JSON, führen Sie einen Code-Formatter aus), dann Line-Diff. Oder wechseln Sie zu Word-Diff, das lange Zeilen korrekt behandelt. Die meisten Online-Tools bieten beides - wählen Sie basierend darauf, ob die Eingabe natürlich zeilenstrukturiert ist.

Wann Git-Diff Wert über Line-Diff hinzufügt

Drei Dinge, die Git verfolgt, die reines Line-Diff nicht kann:

  • Datei-Umbenennungen. Verschieben Sie eine Datei von src/foo.js nach src/bar.js. Line-Diff zeigt es als "ganzes foo.js gelöscht, ganzes bar.js hinzugefügt". Git-Diff mit Umbennen-Erkennung zeigt es als "foo.js umbenannt zu bar.js" plus jegliche tatsächlichen Inhaltsänderungen.
  • Datei-Modus-Änderungen. Ein Skript als ausführbar zu markieren erscheint im Git-Diff als Modus-Änderung ohne Inhalts-Delta. Line-Diff verfehlt es vollständig.
  • Binärdatei-Änderungen. Git-Diff sagt "binary files differ", ohne zu versuchen, die Bytes zu rendern. Line-Diff produziert unlesbare Ausgabe für jede Binär-Eingabe.

Wählen Sie das richtige für die Aufgabe

Vergleichen zweier eingefügter Strings: Text-Diff. Prüfen von Code-Änderungen: Line-Diff oder Git-Diff, wenn Sie Repository-Kontext haben. Prüfen von Copy-Edits: Word-Diff. Untersuchen eines unerwarteten Produktions-Drifts: Text-Diff zuerst, um zu bestätigen, dass der Unterschied existiert, dann Line-Diff, um ihn zu lokalisieren. Das text-diff-Tool deckt die ersten drei ab; Git-Diff lebt innerhalb von Git selbst. Das vollständige Developer-Set ist unter dem Developer-Tools-Hub.
