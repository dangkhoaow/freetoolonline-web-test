Depth: telling seconds from milliseconds, and the Year 2038 limit

Because a Unix timestamp is just a count of seconds from 00:00:00 UTC on 1 January 1970 with no zone baked in, the quickest field check is the digit count: a 10-digit integer is seconds and falls between September 2001 (1000000000) and November 2286 (9999999999), while a 13-digit integer is milliseconds for any present-day moment. If a converted date lands back in 1970 or drifts absurdly far ahead, the remedy is mechanical - multiply a seconds value by 1000 before a milliseconds API, or divide by 1000 before a seconds one. The digit count will not warn you about the Year 2038 problem, though: a signed 32-bit counter maxes out at 2147483647 seconds, which is 2038-01-19 03:14:07 UTC, and one tick later it overflows and wraps back to December 1901, so any service still holding time in a 32-bit int will quietly report the wrong century. The fix is a 64-bit counter, already the default on modern 64-bit builds of Linux and macOS and the mainstream language runtimes, which lifts the ceiling to roughly 292 billion years. Store and transmit the raw integer rather than a pre-formatted local string, and every one of these checks stays reliable no matter which machine reads the value.
