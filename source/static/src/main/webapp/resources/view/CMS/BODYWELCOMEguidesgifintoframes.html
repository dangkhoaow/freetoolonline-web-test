A GIF is one file that plays as motion; the individual frames inside it are the still images that make up that motion. When the goal is to grab one frame for a thumbnail, separate every frame for a storyboard, or rebuild the sequence in a different editor, the extractor reads the animation, splits it on the timeline, and writes each frame to a separate PNG or JPG file. The animation stays intact; the output is a new set of stills sitting alongside the source.

Frame counts, input formats, and what changes between a short loop and a long capture

The extractor accepts three inputs - a .gif, an .mp4, or a .mov - and walks the same path for each, so a 12-frame button-hover loop and a 600-frame screen recording both split cleanly without re-encoding the source first. Because the source is read frame by frame rather than transcoded, a short loop finishes almost instantly while a long capture simply produces a longer preview strip; the original timing and colour of the animation are left untouched. That preview strip lists every frame in playback order, which is what makes single-frame picking practical - the first frame for a cover image, the peak-motion frame for a reaction still, or the final frame for an end-card. Each saved frame can be written as PNG or JPG: pick PNG when the frame will be re-cropped, composited, or needs its transparency preserved, and pick JPG when the frame is a finished delivery asset where a smaller file matters more than pixel-exact edges. From there the workflow branches two ways - download the one frame you selected, or grab the whole set in a single action - so a full storyboard export and a one-off thumbnail pull use the same controls. What it will not do is invent frames that were never captured or re-wrap the animation into WebP or animated PNG; the output is always the stills that already exist inside the source.
