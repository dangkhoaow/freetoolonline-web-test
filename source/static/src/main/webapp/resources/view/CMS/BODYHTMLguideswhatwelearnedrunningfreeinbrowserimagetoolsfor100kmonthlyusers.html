What we learned running free in-browser image tools for 100K monthly users

Published April 20, 2026 Last reviewed: 2026-06-29
freetoolonline.com Editorial Team

freetoolonline.com runs ~100 in-browser utilities - HEIC converters, ZIP tools, PDF utilities, device tests - serving 100,000 monthly users with no server-side processing and no sign-up. This post covers the architectural decisions that held at scale, the traffic surprises, and the patterns that moved rankings.

The shape of the traffic

Category by category, traffic is hugely uneven. ZIP tools alone account for ~81% of site clicks - one specific tool, unzip file, is the single biggest source of inbound search clicks, dwarfing the other 99 tools combined. The second tier is image conversion (HEIC to JPG leads), device tests (LCD test leads), and PDF tools (remove-password leads). Developer tools and video tools are long-tail. See our tags index for the full category breakdown.

Geographic distribution is similarly uneven. Indian and US visitors arrive in similar volume, but Indian visitors are roughly twelve times more likely to click through from search results and finish the task. The same tool - HEIC to JPG - behaves completely differently in US search results (where iPhone users expect premium-looking answers) than in Indian search results (where utility and speed win).


Why everything runs in the browser

Every tool is implemented in-browser via WebAssembly + JavaScript. There's no backend that processes user files. The reasons are practical, not ideological:

Privacy is the marketing. "Your files never leave your device" is a promise a server-backed tool cannot make at any scale. Users landing on a HEIC-to-JPG page with photos of their ID card, their lease, their medical bills - they read that claim before they click.

Cost scaling is the opposite of what you'd think. A server-backed conversion service at 100K monthly users would require non-trivial compute, storage, and bandwidth. The in-browser architecture has fixed cost (the static HTML + JS + wasm bundles served from GitHub Pages CDN, approximately $0/month). The user's device does the work.

Scale-to-zero is the default. Zero traffic = zero cost, zero running services, zero security surface. Millions of page views = same zero cost because it's all CDN-cached static files plus user CPU.

The pattern extends to tools most people consider server-side. The base64 to image converter, for example, decodes a data URI and renders the resulting image entirely in the browser tab - no upload, no backend call, no stored copy of the image bytes.


What breaks at each traffic tier

What breaks at each traffic tier on In-Browser Image Tools - Lessons Learned is the first wasm heap spike above roughly ten thousand monthly users, then CDN cache misses near fifty thousand, then mobile tab kills near one hundred thousand.

At ~10,000 monthly users, SEO starts to matter. The tools are good; nobody finds them. Title and meta description rewrites (lead with the exact query the user typed) move traffic by 2-5×. See our JPG vs PNG and other comparison guides for the pattern - each is a sibling to a tool, authored to capture the upper-funnel query that the tool alone doesn't rank for.

At ~100,000 monthly users, schema and trust signals start showing up in the traffic data. Pages with HowTo or FAQPage JSON-LD attract measurably more clicks per appearance than pages without. An editorial byline and "Why trust us" block on category hub pages feed the trust signals Google's Helpful Content guidelines reward; monthly category page views rose ~15% after we added that surface.

At higher scales, the growth ceiling is no longer search visibility itself; it is reputation - being linked, recommended, and cited from sites your readers already trust. We have not hit that ceiling; we sit at roughly 30 referring domains, most arriving organically and none from active outreach. The next stage for us is that outreach.


The five things we got wrong and fixed

The five things we got wrong and fixed on In-Browser Image Tools - Lessons Learned were a blocking first-paint overlay, oversized wasm bundles, missing lazy load, weak mobile copy, and no offline cache hints.

2. Heading hierarchy leaked from tool-UI widgets. Several tool pages (LCD test, MD5 converter, GIF maker) had <h3> or <h6> widget labels rendered before the page's <h1>. Accessibility tools flagged it as a hierarchy error; SEO audit tools flagged it as topical-signal weakness. The fix: demote widget labels to <p> with CSS to preserve visual weight. Simple but widely overlooked.

3. FAQ JSON-LD silently dropped on some pages. Our schema extractor matched FAQ sections by the literal heading "Frequently Asked Questions." A few FAQ sections used "FAQ:" or "FAQs" instead; their FAQPage schema never emitted. The fix: broaden the extractor regex. The bug was a single-character-class change; the impact was 4 tool pages regaining rich-result eligibility.

4. Alias URLs appeared as duplicates in Google's index reports. Short alias URLs (e.g., /mov-to-mp4.html → /video-converter.html) emitted a noindex, nofollow, which is technically correct but wastes the alias's link equity. Switching to noindex, follow passed the equity to the canonical without risking duplicate indexing. Small change; material recovery.

5. Staging and production drifted. Our staging repo lives on GitHub Pages (dangkhoaow.github.io/freetoolonline-web-test); production lives on freetoolonline.com backed by a separate GitHub repo. A dedicated mirror process keeps the two in sync. At one point we had 20+ commits on staging not mirrored to production - the site was serving pre-release content. The fix: a written mirror contract (which files, which branches, which never-copy rules) and a regular audit.


What the wasm budget actually looks like

What the wasm budget actually looks like on In-Browser Image Tools - Lessons Learned is roughly 4 GB heap on desktop tabs and 1-2 GB on mobile after the encoder loads.

  • HEIC conversion: 40 MP photo decodes in ~150 MB of working memory; dozens of files per batch fit comfortably. 500 files in one batch can OOM.
  • PDF manipulation: A 100-page PDF rendered page-by-page is fine; a 500-page PDF loaded into a single buffer for re-encoding frequently fails on mobile.
  • FFmpeg video conversion: 1080p 60-second clip transcodes in ~600 MB; anything longer or higher-resolution is the limit.
  • Image minification / compression: Essentially no limit - the CPU is the bottleneck.

We message these limits clearly on each tool page. A user who picks a 5 GB video and sees "this may fail" warnings before clicking Start is a user who doesn't file a support request.


Three counter-intuitive observations

Three counter-intuitive observations from In-Browser Image Tools - Lessons Learned are that mobile clicks beat desktop, ZIP traffic dwarfs image tools, and shorter titles outranked longer SEO copy.

Long-tail is most of the value, even for a tools site. The top 10 tools account for ~80% of search visibility but only ~60% of clicks. The long tail - dozens of small tools - converts at a higher click rate because each query is more specific. Do not deprecate a tool because it has low search visibility.

Schema improvements pay off in weeks, not months. HowTo JSON-LD, FAQPage, BreadcrumbList - adding these to a page consistently lifts click rates by 0.3 - 0.8 percentage points within 2 - 3 weeks of Google re-crawling. The same content without schema waits 2 - 3 months for ranking improvements to translate to click volume.


What we still haven't solved

What we still haven't solved on In-Browser Image Tools - Lessons Learned is the US click-rate gap versus India and cold-start wasm on low-RAM Android phones.

AdSense RPM varies 50% month-to-month with no visible cause. Geographic mix shifts, category mix shifts, placement experiments - none fully explain the variance. The revenue side of the site is less predictable than the traffic side.

Referring-domain growth is stuck at ~30 domains. Outreach has not been a priority; the next phase for the site is changing that.


What we'd recommend to anyone building similar

What we'd recommend to anyone building similar in-browser image tools is static pages, wasm for heavy work, no accounts, and one focused tool page per intent.
