Which extraction mode to use

Use the in-browser panel when the GIF should stay on your device or you want WebP and per-frame selection; use the server uploader when the GIF is too large to decode reliably in a browser tab.

Upload mode extracts on the server: the GIF uploads, frames decode remotely, and the result returns via a short-lived download URL backed by temporary storage that rotates off after the platform's auto-delete window. The trade-off is that the GIF leaves your device, so check that against any sensitivity policy first.

The in-browser panel below the uploader decodes frames locally instead, with nothing leaving the browser tab: all frames, every Nth frame, or a specific comma-separated list; an optional max-width resize; and PNG, JPG, or WebP with a quality slider. It needs a browser that supports the underlying decoder, and where that support is missing the panel shows a plain notice pointing back to the server upload above.

What to do with the extracted frames

Two uses cover most jobs: a sprite sheet, or one still standing in for the whole animation. Lined up side by side in an image editor, the frames build a sprite sheet - a strip of images used as one asset in games or simple animations. Or keep a single representative frame as a lightweight stand-in: one JPG frame is typically a fraction of the original GIF's file size, so a page or email that shows it instead of the full animation loads faster for a reader on a slow connection.

From an extracted frame to a base64 string

If your next step is embedding one of the extracted stills straight into HTML or CSS instead of linking to a file, take the saved frame to the image to base64 converter, which turns a single picture into a data-URI string you can paste inline.
