Which extraction mode to use

Upload mode extracts on the server: the GIF uploads, frames decode remotely, and the result returns via a short-lived download URL backed by temporary storage that rotates off after the platform's auto-delete window. Pick it when the source GIF is too large to decode reliably in a browser tab, or when you are on a mobile network and prefer the heavy lifting done elsewhere - the trade-off is that the GIF leaves your device, so check that against any sensitivity policy first.

The in-browser panel below the uploader decodes frames locally instead, with nothing leaving the browser tab: all frames, every Nth frame, or a specific comma-separated list; an optional max-width resize; PNG, JPG, or WebP with a quality slider; and download one frame at a time or all of them zipped. It needs a browser that supports the underlying decoder, and where that support is missing the panel shows a plain notice pointing back to the server upload above.

What to do with the extracted frames

Each frame saves out as its own PNG or JPG file, so several frames can be lined up side by side in an image editor to build a sprite sheet - a strip of images used as one asset in games or simple animations. Or keep just one representative frame as a lightweight stand-in for the whole GIF: a single JPG frame is typically a fraction of the original GIF's file size, so a page or email that shows one frame instead of the full animation loads faster for a reader on a slow connection.

From an extracted frame to a base64 string

If your next step is embedding one of the extracted stills straight into HTML or CSS instead of linking to a file, take the saved frame to the image to base64 converter, which turns a single picture into a data-URI string you can paste inline.
